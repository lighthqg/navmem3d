# 下午方案复盘总结

## 结论

下午已经形成的正确方向，是把两个互补信息层叠加起来：

1. **空间观测层**：机器人巡视时由 RGB-D/LiDAR 和位姿建立的二维空间表示，至少包含可通行区域、障碍物的大致轮廓和未知区域。
2. **拓扑路线层**：在巡视路径上维护的无向连通图，节点绑定巡视关键帧，边表示已经实际走过或确认连通的路线。

用户要的是这两层的加和，而不是用第二层替换第一层，也不是要求第一版立即从不可靠的深度近似重新推导完整骨架。

## 下午真正确认的系统边界

系统有三个世界：

- **A / InteriorGS**：评测场地。为机器人提供 RGB、深度/LiDAR、相机位姿，并提供隐藏真值做评测。隐藏 occupancy、labels、structure 不能作为系统输入。
- **B / Marble**：高质量三维语义世界。提供实体类别、属性、实例、虚拟视角和语义查询结果。
- **M / Robot map**：机器人自己的观测地图与路线数据。它不需要复制 Marble 的几何，也不应把 Marble 当作控制器地图。

语义交接是：

```text
Marble entity_id
→ 该实体对应的巡视观察帧/观察区域
→ M 中的路线节点或节点集合
→ 无向图近似最短路
→ 当前 RGB/LiDAR/VIO 执行与到达确认
```

## 关键决策的正确含义

### 1. 拓扑图不是巡视折线的简单画法

下午反复指出了 `T023 → T004` 这类问题：

- 几何线段相交，不等于图数据中存在可转入节点；
- 相邻节点靠得近，不等于它们连通；
- 图必须表达连通性，而不是把所有几何邻近关系都连起来；
- 节点可以稀疏，但关键枢纽和分叉必须存在；
- 每个骨架节点附近需要关键帧，橙色视觉锚点不应作为额外路线节点层。

因此，原有 41 节点/48 边的拓扑原型虽然还不是最终的 occupancy-derived 图，但其数据结构比后来的“邻近节点全部 A* 连边”正确得多。

### 2. 障碍物与拓扑需要同时呈现

下午最后提出的要求不是“再画一张图”，而是系统输出应支持：

```text
底图：观测到的可通行区域 + 障碍物大致轮廓 + unknown
上层：拓扑节点 + 无向边 + 路线高亮
```

障碍物不要求精确 mesh，只要能说明为什么某些地方不能直穿、为什么路线绕行即可。这个联合地图是调试、评测和向人解释路线的统一视图。

### 3. 深度是观测输入，不是自动获得的真值地图

如果 A 能提供相机深度或模拟 LiDAR，机器人可以据此建立自己的观测 occupancy。深度的作用是支持障碍轮廓和自由空间观测；它不能自动决定拓扑图的连通关系。拓扑仍需根据实际巡视轨迹、局部自由空间连通性和节点维护规则编译。

## 后来出现的偏差

### 偏差一：把“联合显示”误解成“重做 occupancy-derived topology”

在后续实现中，系统直接用 CPU Gaussian 中心 z-buffer 生成深度，再从稀疏深度重建 occupancy 和拓扑。这一步把一个验证问题变成了主链路：

- 高斯中心不是连续表面；
- 深度覆盖存在大量空洞；
- unknown 被大量误当成空间缺失；
- 从不完整 occupancy 提取骨架必然不稳定。

这个 fallback 可以作为诊断实验，不能成为第一版拓扑的依据。

### 偏差二：把“附近可达”当成“拓扑边”

第一次观测拓扑输出 38 个节点、105 条边。根因是对每个节点找附近节点并运行 A*，这会在同一自由空间中制造大量虚假捷径，破坏连通图的语义。

第二次直接做稀疏骨架后得到 99 个节点、1 条边、97 个孤立点，说明输入和骨架提取都不满足验收条件。

### 偏差三：把中间诊断产物包装成第一版完成

目前 `observed_map` 下的 occupancy/topology 只能说明“链路接口已经写出来”，不能说明导航地图已经正确。下午的原始目标是先把可用工程闭环做出来，应该保留可靠的路线拓扑，同时把 occupancy 作为空间解释层叠加，而不是用失败的 occupancy 结果替换可靠骨架。

## 与两张图的对应关系

用户给出的两张图正好对应正确架构：

- 第一张：带障碍物和可通行区域的巡视空间图，回答“哪里能走、哪里被挡住”；
- 第二张：节点和边的无向拓扑图，回答“图数据认为哪些位置连通、路线如何搜索”。

系统应该生成一张联合视图，同时保留两份原始数据：

```text
observed_space_map
  - free / occupied / unknown
  - obstacle contours
  - metric transform

patrol_topology_graph
  - topology nodes
  - undirected edges
  - edge polylines and costs
  - reference keyframes
```

联合视图只是这两份数据的渲染，不承担地图推理本身。

## 正确的第一版推进顺序

1. 保留并清理原有巡视拓扑骨架：使用 41/48 原型作为当前路线图基线，确认节点、无向边、关键帧和图搜索字段一致。
2. 生成空间观测层：优先使用真实可用的 depth/LiDAR；没有可靠深度时，不伪造精确 occupancy，只输出观测覆盖和障碍轮廓置信度。
3. 建立联合地图渲染器：输入 `observed_space_map + patrol_topology_graph`，自动叠加障碍轮廓、free/unknown、拓扑节点和无向边。
4. 用 Marble B 实体绑定到拓扑节点/观察区域，不要求 Marble 给控制器几何坐标。
5. 在无向拓扑上做 Dijkstra/A*，输出节点序列、边序列、参考关键帧序列和当前 RGB 到达确认。
6. 之后再研究从完整观测 occupancy 自动提取骨架。它是增强项，不应阻塞第一版工程论文闭环。

## 当前文件状态的解释

- `topology_graph_final.json`：旧拓扑原型，41 节点、48 边；目前仍是最可信的路线骨架基线。
- `visual_route_graph.json`：22 个视觉关键帧路线图，适合执行回放和视觉重定位。
- `observed_map/observed_occupancy.*`：CPU Gaussian 深度 fallback 生成的诊断产物，输入质量不足。
- `observed_map/topology_graph_observed.json`：对 occupancy 自动提拓扑的失败实验，不应作为正式导航图。
- `entity_topology_binding_observed.json`：接口验证产物，后续应重新绑定到可靠的基线拓扑。

## 最终判断

下午的核心思想没有问题：**Marble 负责高质量三维语义，机器人自己的地图负责路线和执行，空间观测层与拓扑层并存并叠加。**

真正的问题是后来把“空间层 + 拓扑层的加和”错误实现成了“仅凭低质量深度重新生成拓扑”。下一步应回到双层数据结构和联合可视化，而不是继续调整当前失败的 occupancy-derived 拓扑参数。
